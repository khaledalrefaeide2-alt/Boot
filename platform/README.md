# منصة رصد وتحليل المنصات الإعلامية

نظام داخلي خاص لرصد وتحليل المحتوى المنشور على **فيسبوك** و**إكس** و**إنستغرام**،
عبر متابعة حسابات وصفحات محددة واستخراج منشوراتها من Apify وتخزينها وتحليلها وعرضها.

الواجهة عربية بالكامل، الاتجاه RTL، التصميم رسمي حكومي هادئ، مع وضع فاتح وداكن،
وتخطيط متجاوب يعمل على الجوال وعلى شاشة كبيرة في غرفة العمليات.

| Redis | 7 |
| Docker و Docker Compose | لتشغيل كل شيء بأمر واحد |

## التشغيل السريع عبر Docker

```bash
# ويندوز — انقر على الملف نقرتين، أو نفّذ:
.\setup.bat

# ماك أو لينكس
bash setup.sh
```

> **ويندوز:** إن فضّلت تشغيل سكربت PowerShell مباشرة فسيمنعه النظام برسالة
> `running scripts is disabled on this system`. استخدم `setup.bat` أعلاه، أو نفّذ:
> ```powershell
> powershell -NoProfile -ExecutionPolicy Bypass -File .\setup.ps1
> ```
> كلاهما يتجاوز القيد لهذه المرة فقط ولا يغيّر أي إعداد أمني في نظامك.

يسألك السكربت عن كلمة مرور القاعدة وبريدك واسمك وكلمة مرور دخولك ورمز Apify،
ثم يولّد مفتاح الجلسات ويكتب ملف `.env` بصيغة سليمة. بعدها:

```bash
docker compose up -d --build
```

> لتحرير الإعدادات يدوياً بدل السكربت: انسخ `.env.example` إلى `.env` وغيّر القيم
> المعلّمة بـ (مطلوب). **اكتب القيم بحروف لاتينية** — القيم العربية داخل ملف البيئة
> تُربك المحررات على ويندوز وقد تُفقد علامة `=` فيفشل التشغيل.

يعمل النظام على `http://localhost:3000` — منشور على الجهاز المحلي فقط.

يقوم التشغيل تلقائياً بـ:
1. تطبيق مهاجرات قاعدة البيانات.
2. تهيئة البيانات الأولية (المالك الأول، المنصات الثلاث، التصنيفات، الإعدادات).
3. تشغيل تطبيق الويب والعامل الخلفي في حاويتين منفصلتين.

## التشغيل للتطوير

```bash
npm install
cp .env.example .env          # ثم عدّل القيم
npm run setup:db              # الترحيلات + البيانات الأولية + حساب المالك
npm run dev                   # تطبيق الويب
npm run worker                # العامل الخلفي — في نافذة أخرى
```

`setup:db` آمن للتكرار: لا يعيد إنشاء ما هو موجود ولا يغيّر كلمة مرور المالك.
**تخطّي هذه الخطوة يعني عدم وجود أي حساب**، فيفشل تسجيل الدخول برسالة
«البريد الإلكتروني أو كلمة المرور غير صحيحة» مهما كانت البيانات صحيحة.

## متغيرات البيئة

كل الأسرار في ملف البيئة فقط، ولا يُخزَّن أي منها في قاعدة البيانات ولا يصل إلى المتصفح.

| المتغير | الوصف |
|---|---|
| `DATABASE_URL` | رابط PostgreSQL |
| `REDIS_URL` | رابط Redis للطوابير والتخزين المؤقت وتحديد المعدل — يجب أن تكون سياسة الذاكرة فيه `noeviction` |
| `SESSION_SECRET` | مفتاح توقيع الجلسات — 32 محرفاً على الأقل (`openssl rand -base64 48`) |
| `SESSION_TTL_DAYS` | عمر الجلسة بالأيام (افتراضي 7) |
| `APP_URL` | عنوان التطبيق — يُستخدم للتحقق من مصدر الطلبات (حماية CSRF) |
| `APP_ALLOWED_ORIGINS` | عناوين إضافية موثوقة مفصولة بفواصل — للوصول من أجهزة أخرى على الشبكة المحلية |
| `APIFY_TOKEN` | رمز Apify — **خادمي بحت** |
| `APIFY_MAX_ITEMS_HARD_CAP` | سقف صارم لعدد العناصر في أي تشغيل مهما كانت إعدادات الحساب |
| `APIFY_RUN_TIMEOUT_SECONDS` | مهلة انتظار انتهاء التشغيل |
| `SEED_OWNER_EMAIL` / `SEED_OWNER_NAME` / `SEED_OWNER_PASSWORD` | حساب المالك الأول — يُنشأ مرة واحدة فقط |

## الأدوار والصلاحيات

| الدور | الصلاحيات |
|---|---|
| **OWNER — مالك المنصة** | كل شيء، بما فيه الأدوار والإعدادات الحساسة |
| **ADMIN — مدير النظام** | إدارة المستخدمين والموافقات والإعدادات، والاطلاع التشغيلي الكامل |
| **SUPERVISOR — مشرف** | المنصات والحسابات والاستخراج ومراجعة البيانات والتصنيف والقوالب والسجلات |
| **VIEWER — مستخدم عادي** | مشاهدة اللوحات والبحث والفلترة والمقارنة والتصدير وحفظ لوحاته فقط |

مصفوفة الصلاحيات مصدرها ملف واحد (`src/lib/auth/rbac.ts`) وتُطبَّق في الواجهة وفي كل مسار API معاً.

### لماذا تبقى العملية «بانتظار التشغيل»؟

إنشاء العملية وتشغيلها خطوتان منفصلتان. الموقع ينشئ العملية ويضعها في الطابور، ثم **العامل
الخلفي** يسحبها منه ويستدعي Apify. فبلا عامل تُنشأ العمليات وتبقى بانتظار التشغيل حتى تنتهي
مهلتها، ولا يصل إلى Apify شيء.

العامل نافذة أوامر مستقلة تعمل بجانب الخادم ويجب أن تبقى مفتوحة:

```bash
npm run worker
```

شاشة عمليات الاستخراج تقرأ عدد العمال المتصلين بالطابور فعلاً وتُعلن غيابه بشريط أحمر مع
الأمر الذي يعيده. وكذلك رسالة التشغيل نفسها: لو شُغّلت عملية ولا عامل، قالت ذلك في حينه بدل
أن يكتشفه المستخدم بعد نصف ساعة.

قياس عدد العمال يمرّ بأمر `CLIENT LIST` في Redis. إن منعته خدمة Redis (بعض الخدمات المُدارة
تفعل) عُدّ العدد «غير معلوم» ولم يُرفع إنذار، لأن تعذّر القياس ليس غياب عامل.

### تشغيل الاستخراج على عدة حسابات دفعةً واحدة

في شاشة إدارة الحسابات عمود تحديد بجانب كل حساب، ومربع في ترويسته يحدّد الصفحة كاملة. عند
تحديد حساب واحد فأكثر يظهر شريط يعرض العدد وزرّ «استخراج جماعي». التحديد يبقى عبر الصفحات
وتغيير الفلاتر، فما اختير في عرض سابق يُشغَّل معها.

النافذة تطلب الفلاتر نفسها التي يطلبها التشغيل الفردي — النطاق الزمني وأقصى عدد للمنشورات —
وتُطبَّق على المحدَّد كله. والخيارات الخاصة بمنصة (ترتيب نتائج إكس، نوع محتوى إنستغرام) لا
تظهر إلا إن كان بين المحدَّد حساب عليها، ولا تُمرَّر إلى حسابات المنصات الأخرى.

الدفعة ليست معاملة واحدة: كل حساب عملية مستقلة على حصة Apify، وفشل واحد لا يبطل ما نجح.
فيُعرض بعد التشغيل تقرير بحال كل حساب — بدأت، أو لم تبدأ ولماذا: معطّل، أو لديه عملية قائمة،
أو منصته بلا Actor. والحسابات التي لم تبدأ لم يتغيّر فيها شيء وتقبل إعادة المحاولة.

الحصة الساعية تُفحص قبل البدء لا أثناءه: لو كان المتبقي أقل من عدد المحدَّد رُفضت الدفعة كلها
وذُكر المتبقي بالعدد، فلا تخرج دفعة نصفها منفَّذ. وزر «استخراج» على الصف الواحد يفتح النافذة
نفسها بحساب واحد، فالفلاتر مفروضة في الحالتين.

### استيراد الحسابات من ملف Excel

بدل إضافة الحسابات واحداً واحداً، من شاشة إدارة الحسابات زرّ «استيراد من Excel».

القالب يُنزَّل من داخل النافذة، وفيه الأعمدة الأحد عشر وورقة ثانية تشرح القيم المقبولة لكل
عمود وتسرد المنصات المسجلة عندك:

| العمود | إلزامي | ملاحظة |
|---|---|---|
| المنصة | نعم | بالاسم العربي أو بالرمز اللاتيني |
| اسم الحساب | نعم | |
| رابط الحساب | نعم | وهو ما يميّز الحساب: لا يتكرر على المنصة نفسها |
| اسم المستخدم | لا | |
| المعرّف الخارجي | لا | |
| نوع الحساب | لا | صفحة، حساب شخصي، مجموعة، قناة، أخرى |
| الملكية | لا | حساب نملكه، جهة أخرى |
| الظهور | لا | عام، خاص |
| اللغة | لا | ar أو en |
| الدولة | لا | |
| الحالة | لا | نشط، متوقف |

القراءة متسامحة والتحقق ليس كذلك: العناوين تُطابق بعد تجريدها من التشكيل والهمزات، والقيم
تُقبل بالعربية كما تظهر في الشاشة وبالرمز الإنجليزي معاً، والخلايا الاختيارية الفارغة تأخذ
القيم الافتراضية. أما الصف الذي لا يستوفي الشروط فيُرفض بسببه مكتوباً.

الاستيراد على خطوتين: الرفع يعرض حكم كل صف (جاهز، مكرر، خطأ) قبل أن يُكتب شيء، ثم يؤكّد
المستخدم فتُحفظ الصفوف الجاهزة وحدها في معاملة واحدة. المكرر لا يُعدَّل ولا يُحذف. وإعدادات
الاستخراج تأخذ الافتراضيات وتُضبط لاحقاً من شاشة الحساب. الحدّ ٥٠٠ صف في الملف الواحد،
والعملية تُسجَّل في سجل التدقيق.

### نطاق الحسابات — من يرى بيانات مَن

الدور يقول *ماذا* يفعل المستخدم، والنطاق يقول *على أي بيانات*. لكل مستخدم وضعان:

- **كل الحسابات** — الافتراضي، يرى بيانات كل حساب مرصود.
- **حسابات محددة** — لا يرى إلا بيانات الحسابات المُسندة إليه.

يُضبط من صفحة إدارة المستخدمين بزر «تحديد الحسابات التي يصل إليها» بجانب المستخدم، ويحتاج
صلاحية إدارة الأدوار. الحصر يشمل: المنشورات وتفاصيلها، الإحصاءات والرسوم، المقارنة، التصدير،
قوائم الحسابات والمنصات وخيارات الفلاتر، وسجل الاستخراج.

ثلاث نقاط تستحق الانتباه:

- الحصر يقع في طبقة الاستعلام لا في الواجهة، والتقاطع على ما هو مسموح لا على ما طُلب: تمرير
  معرّف حساب في معاملات الطلب لا يتجاوز القيد.
- ما هو خارج النطاق يردّ «غير موجود» لا «ممنوع»، فلا يؤكّد الردّ وجود معرّف جُرّب عشوائياً.
- المستخدم المقيّد لا يتلقّى تنبيهات النظام العامة، لأن عناوينها تحمل أسماء حسابات قد تكون
  خارج نطاقه.

**لا يوجد تسجيل ذاتي.** الحسابات تُنشأ يدوياً من الإدارة، وحالة المستخدم إحدى ثلاث:
`pending` (بانتظار الموافقة) أو `active` (مفعّل) أو `disabled` (معطّل).

### استعادة كلمة المرور

لا يوجد إرسال بريد في النسخة الأولى. الآلية:
- المستخدم يطلب الاستعادة من صفحة الدخول → يصل تنبيه داخلي للمدراء برابط صالح ساعة واحدة.
- أو المدير يولّد رابط استعادة مباشرة من صفحة إدارة المستخدمين.
- يُسلَّم الرابط للمستخدم بقناة موثوقة، ويُستخدم مرة واحدة فقط.

إضافة SMTP لاحقاً لا تتطلب أي تغيير في المخطط.

### الفتح من الجوال على الشبكة المحلية

المنصة تعمل على جهازك، وللوصول إليها من جهاز آخر على الشبكة نفسها:

**١)** اعرف عنوان جهازك على الشبكة:

```powershell
(Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.IPAddress -notlike '127.*' }).IPAddress
```

**٢)** أضف العنوان إلى العناوين الموثوقة في ملف `.env` — فحص مصدر الطلب
يرفض ما لم يُدرَج، فبدون هذه الخطوة يفشل تسجيل الدخول برسالة «مصدر الطلب
غير موثوق»:

```
APP_ALLOWED_ORIGINS="http://192.168.1.20:3111"
```

**٣)** اسمح للمنفذ في جدار حماية ويندوز (مرة واحدة، بصلاحية مسؤول):

```powershell
New-NetFirewallRule -DisplayName "Media Monitoring 3111" -Direction Inbound -LocalPort 3111 -Protocol TCP -Action Allow
```

**٤)** أعد تشغيل الموقع، ثم افتح من الجوال:  `http://192.168.1.20:3111`

**تنبيه أمني:** هذا يجعل المنصة متاحة لكل من على الشبكة نفسها، والاتصال بلا
تشفير فتنتقل كلمات المرور نصاً مقروءاً. لا تفعله إلا على شبكة موثوقة، وأزل
العنوان من `APP_ALLOWED_ORIGINS` عند انتهاء الحاجة. للاستخدام الدائم يلزم
نشر المنصة على خادم بشهادة HTTPS.

### المنفذ مشغول

رسالة `EADDRINUSE` تعني أن نسخة سابقة من الخادم ما زالت تعمل — غالباً في نافذة
أخرى لم تُغلق. أغلق تلك النافذة، أو حرّر المنفذ:

```powershell
Get-NetTCPConnection -LocalPort 3111 -ErrorAction SilentlyContinue | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

إن لم يُطبع الأمر شيئاً فالمنفذ حرّ أصلاً، وهذه هي الحالة المطلوبة.

**مهم:** ما دام المنفذ مشغولاً بالنسخة القديمة فالموقع الذي تراه في المتصفح هو
النسخة القديمة بإعداداتها القديمة. أي تعديل على ملف `.env` — رمز Apify مثلاً —
لا يسري حتى تتوقف تلك النسخة فعلاً ويبدأ الخادم من جديد.

### الوسائط لا تظهر

نخزّن روابط الوسائط ولا نحمّل الملفات، والرابط يجب أن يكون **ملف** وسائط لا
صفحة عرض. بعض الـ Actors تضع الرابط الدائم للمنشور في حقل يبدو حقل وسائط
(`facebook.com/photo/?fbid=…`)، والمتصفح يطلبه فيستقبل صفحة HTML لا صورة.

المحوّل يرفض الآن كل رابط ليس ملف وسائط، ويستنتج نوع المنشور من شكل رابطه
الدائم بدلاً من ذلك. لتنظيف ما خُزّن قبل هذا الإصلاح:

```bash
npm run media:repair              # عرض ما سيُصلح دون تغيير
npm run media:repair -- --apply   # تنفيذ الإصلاح
```

المحوّل يبحث عن الوسائط في عمق مخرجات الـ Actor لا في مسارات ثابتة، لأن
بنية المخرجات تختلف بين Actor وآخر وتتغيّر مع إصداراته. ويتخطّى الفروع التي
لا تحوي وسائط المنشور: أشرطة معاينة تمرير الفيديو وصور الحسابات والأيقونات.

إن بقيت المنشورات بلا صور بعد ذلك، فالـ Actor نفسه لا يُرجع روابط ملفات
الوسائط — عندها يلزم تغيير الـ Actor أو ضبط مدخلاته ليُرجعها.

### تعذّر تسجيل الدخول

إن ظهرت رسالة **«تم إيقاف المحاولات مؤقتاً بسبب تكرار الفشل»**، فالحساب موقوف بعد
محاولات فاشلة متتالية. أمامك ثلاثة حلول:

- **الانتظار ١٥ دقيقة** — يُرفع الإيقاف تلقائياً.
- **من لوحة الإدارة** — تعطيل الحساب ثم تفعيله، أو توليد رابط استعادة له. كلاهما
  يرفع الإيقاف فوراً.
- **من سطر الأوامر** إذا كان الحساب الموقوف هو حساب المالك نفسه:

  ```bash
  npm run owner:reset -- "كلمة-المرور-الجديدة"
  ```

  يعرض الأمر كل حسابات النظام، ويعيد تعيين كلمة مرور المالك، ويرفع القفل والعدّادات
  من قاعدة البيانات ومن Redis معاً، فيمكن الدخول فوراً دون انتظار.

## ربط Apify

- كل نداءات Apify تتم **من الخادم أو العامل الخلفي فقط**. الرمز يُرسل في ترويسة `Authorization`
  ولا يظهر في الروابط ولا في السجلات ولا يصل إلى المتصفح إطلاقاً.
- **سقف الفوترة**: يُمرَّر `maxItems` إلى Apify كسقف إلزامي تفرضه المنصة نفسها على التشغيل،
  ويُقيَّد إضافياً بـ `APIFY_MAX_ITEMS_HARD_CAP` من ملف البيئة. لن تُحاسَب على أكثر من العدد المحدد.
- البيانات تُخزَّن في قاعدة بيانات النظام، وليس داخل Apify فقط.

### الـ Actors الافتراضية

| المنصة | الـ Actor |
|---|---|
| فيسبوك | `apify~facebook-posts-scraper` |
| إكس | `apidojo~tweet-scraper` |
| إنستغرام | `apify~instagram-scraper` |

قابلة للتعديل لكل منصة من **إدارة المنصات**، ولكل حساب على حدة من **إدارة الحسابات**.

عملية لا تدخل الطابور تُنهى فوراً بحالة «فشل» برسالة واضحة، ولا تُترك معلّقة:
العملية المعلّقة تقفل حسابها كلياً لأن التشغيل اليدوي يُرفض لوجود «عملية قائمة»
والجدولة تتخطّى الحساب للسبب نفسه. كذلك يحرّر العامل الخلفي كل عملية تجاوزت
ضعف مهلة Apify، فيتعافى النظام وحده إذا توقف العامل في منتصف تشغيل.

### فلاتر التشغيل اليدوي

كل تشغيل يدوي يتطلب تحديداً صريحاً قبل البدء، ولا يعتمد على أي قيمة محفوظة:

| الفلتر | إلزامي | ملاحظة |
|---|---|---|
| الحساب | نعم | حساب واحد مرصود ومفعّل |
| من تاريخ / إلى تاريخ | نعم | النطاق يُمرَّر للـ Actor ويُفرض عند الاستيراد أيضاً |
| أقصى عدد منشورات | نعم | 1–1000، وهو سقف الفوترة على Apify |
| ترتيب النتائج | لا | إكس وحدها: الأحدث أو الأكثر تفاعلاً |
| نوع المحتوى | لا | إنستغرام وحدها: منشورات أو ريلز |

الإلزام مفروض في الخادم لا في الواجهة وحدها، فلا يمكن تشغيل عملية بلا حدود
معلومة عبر مسار API مباشرةً. والنطاق يُفرض مرتين: يُرسل إلى الـ Actor، ثم
تُستبعد عند الاستيراد أي منشورات خارجه — لأن بعض الـ Actors تتجاهل حد النهاية
أو تُرجع منشورات مثبّتة خارج المدى.

**الجدولة التلقائية** تستعمل إعدادات الحساب (المدة والعدد)، لأنها لا تجد من
يحدد لها شيئاً وقت التشغيل. والنطاق المطلوب لكل عملية محفوظ ويظهر في صفحة
تفاصيلها.

### حالات عملية الاستخراج

`pending` ← `running` ← `succeeded` / `failed` / `cancelled` / `no_results`

لكل عملية سجل يحفظ: تاريخ البدء والانتهاء والمدة، عدد ما جُلب وحُفظ وحُدّث وفشل،
رسالة الخطأ وتفاصيله، عينة خام من النتائج للتشخيص، والمدخلات المرسلة إلى الـ Actor.

### الجدولة التلقائية

لكل حساب حقل «تكرار الاستخراج» بالدقائق (`0` = يدوي فقط). العامل الخلفي يفحص كل دقيقة
الحسابات المستحقة ويضيفها إلى الطابور. حساب متعثر لا يوقف جدولة البقية.

## البيانات المخزّنة لكل منشور

النص، الصورة، الفيديو، الرابط، تاريخ النشر، اسم الحساب، اسم المنصة، الإعجابات، التعليقات،
المشاركات، المشاهدات، الحفظ، نوع المنشور، اللغة، الدولة أو الموقع، المشاعر، الكلمات المفتاحية
المكتشفة، وتصنيف الموضوع.

**ضمانات الاستيراد:**
- كل حقل غير متاح من Apify يُخزَّن `null` — لا يُفترض وجود أي حقل.
- منشور واحد فاسد لا يُفشل العملية كاملة: يُتجاهل ويُحصى ويُسجَّل سببه في صفحة العملية.
- منع التكرار عبر `dedupeKey` (المعرّف الخارجي أو بصمة الرابط) مع قيد فريد لكل حساب —
  المنشور المكرر تُحدَّث أرقام تفاعله فقط ولا يُعاد إنشاؤه.
- **لا تُستخرج التعليقات ولا تُحلَّل إطلاقاً.**

### التحليل

تحليل المشاعر يعمل بقواعد لغوية عربية (تطبيع النص، معالجة النفي)، والتصنيف الموضوعي بقواعد
كلمات مخزّنة لكل تصنيف، ويمكن تصحيح الاثنين يدوياً من شاشة مراجعة البيانات.

الحقول جاهزة في القاعدة (`sentimentSource` و `topicSource` تقبل `RULES` و `MANUAL` و `AI`)
لاستبدال المحرك بنموذج ذكاء اصطناعي لاحقاً دون أي تغيير في المخطط أو الواجهات.

## الأداء والإحصاءات

- جدولا `DailyAccountStat` و `DailyPlatformStat` يُحدَّثان مباشرة بعد كل عملية استخراج،
  وللأيام المتأثرة فقط.
- فهارس على التاريخ والتفاعل والمشاعر والنوع واللغة والدولة، وفهارس GIN مع `pg_trgm`
  للبحث النصي داخل المنشورات وأسماء الحسابات، وفهارس GIN للهاشتاغات والكلمات المكتشفة.
- فشل تحديث الإحصاءات لا يُفشل الاستيراد — البيانات محفوظة ويمكن إعادة البناء
  عبر مهمة الصيانة `rebuild-daily-stats`.

## الأمان

- كلمات المرور مشفّرة بـ bcrypt (12 جولة).
- الجلسات مخزّنة في القاعدة برموز عشوائية مجزّأة بـ HMAC-SHA256 بمفتاح `SESSION_SECRET`،
  وكوكيز `HttpOnly` + `SameSite=Lax` و `Secure` في الإنتاج. تعطيل المستخدم أو تغيير كلمة
  مروره يُبطل جلساته فوراً.
- المفتاح خط دفاع ثانٍ: من يحصل على نسخة من قاعدة البيانات وحدها لا يستطيع مطابقة أي رمز
  جلسة أو استعادة مسرَّب من مكان آخر ما لم يحصل على المفتاح من بيئة الخادم.
  **تغيير `SESSION_SECRET` يُبطل كل الجلسات وروابط الاستعادة القائمة.**
- حماية CSRF بنمط الإرسال المزدوج مع فحص مصدر الطلب على كل عملية مغيّرة.
- تحديد معدل للاستعادة والتصدير والاستخراج والعمليات المغيّرة، عبر Redis مع تدهور
  لطيف إلى ذاكرة العملية.
- حدّ محاولات الدخول **يحسب المحاولات الفاشلة وحدها** (حسب العنوان وحسب البريد)،
  والدخول الناجح يمسح العدّادين معاً. الاستخدام النظامي مهما تكرر لا يقترب من الحد.
- بعد ٨ محاولات فاشلة متتالية على حساب واحد يُقفل الحساب ١٥ دقيقة. عند انقضاء المدة
  يبدأ عدّ جديد من الصفر، ولا يُعاد القفل بمحاولة فاشلة واحدة.
- التحقق من كل المدخلات عبر Zod برسائل خطأ عربية.
- حالة الحساب (بانتظار الموافقة / معطل) لا تُكشف إلا بعد التحقق من كلمة المرور — لا تسريب لوجود الحسابات.
- سجل تدقيق لكل عملية حساسة: من نفّذها ومتى ومن أي عنوان، ولا يُفشل العملية الأصلية عند تعذّر التسجيل.
- ترويسات أمان: `X-Frame-Options: DENY`، `nosniff`، `Referrer-Policy`، ومنع الفهرسة نهائياً.
- الرموز والأسرار لا تصل إلى المتصفح إطلاقاً، والبيانات الخام لا تُعرض إلا لأصحاب صلاحية المراجعة.
- **لا طلبات خارجية من المتصفح**: الخط مستضاف محلياً في `public/fonts`، فلا يخرج أي
  طلب إلى خوادم خارجية عند فتح الصفحات. تعمل الواجهة بهويتها كاملة على شبكة معزولة.
- صور الوسائط وحدها تُطلب من مصدرها لأننا نخزّن الروابط لا الملفات، وتُرسل بسياسة
  `no-referrer` حتى لا يتسرّب عنوان المنصة الداخلية إلى خوادم المنصات، ولها بديل
  محايد يظهر إذا تعذّر تحميلها.

## الاختبار

```bash
npm run typecheck              # فحص الأنواع
npm run build                  # بناء إنتاجي كامل
npm run verify:pipeline        # فحص خط الاستيراد ببيانات تحاكي مخرجات Apify
npm run verify:scope           # فحص حصر البيانات — والخادم يعمل في نافذة أخرى
```

`verify:pipeline` يفحص: بناء مدخلات الـ Actor لكل منصة، تحويل الحقول، تجاهل العناصر الفاسدة
دون إيقاف العملية، الاستيراد، تحليل المشاعر، منع التكرار، وتحديث الإحصاءات اليومية.

`verify:scope` ينشئ مستخدماً مقيّداً بحساب واحد وآخر بلا قيد، ثم يسجّل الدخول بهما فعلاً
ويستجوب كل سطح عبر HTTP — لأن التسريب يسكن في المسار المنسيّ لا في الدالة المشتركة. يحذف
المستخدمَين وكل أثر لهما في النهاية، وينتهي بحالة خروج غير صفرية إن وجد تسريباً.

## ملاحظات تشغيلية

- **الخط**: يُحمَّل Cairo من Google Fonts وقت التشغيل، ويعمل النظام بخطوط النظام العربية
  إذا كانت البيئة معزولة عن الإنترنت.
- **الوسائط**: تُخزَّن الروابط فقط ولا تُحمَّل الملفات إلى الخادم.
- **الاحتفاظ**: سنة كاملة بلا حذف تلقائي في النسخة الأولى.
- **الاستخدام**: النظام أداة داخلية، ويجب ألا يُستخدم إلا بما يتوافق مع السياسات
  والصلاحيات المتاحة للجهة على المنصات المرصودة.
